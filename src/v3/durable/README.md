# V3 durable execution foundation

This is a working, opt-in trusted-host execution kernel backed by Node 24's built-in SQLite. It does not replace the V2 runtime and does not implement an independent Execution Host, OS isolation, encrypted payload storage, generic workflow recovery, or hardware reconciliation.

## Integration

1. Acquire the exclusive Slot owner lock before opening this runtime. A new kernel assumes the previous Core owner is stopped. A SQLite transaction lock alone is not the Core ownership lock.
2. Create `new DurableStore(localPath, { clock?, maxRuns? })`; the directory and database must be protected from untrusted code by the deployment. Do not put the database in an agent-writable Workspace or a network share. The database, WAL, and SHM may contain plaintext input and results; do not put secrets in input. The store does not claim to establish Windows ACLs.
3. Call `createDurableKernel({ store, authorize, revalidate, maxConcurrency? })`. Retain `operator` only in the authenticated local Operator adapter. Remote clients receive only the kernel's explicitly registered public tools, never the store or Operator object.
4. Register immutable capability/version/binding descriptors with `kernel.register`. `execute({ run, input, signal })` must perform its own engineering postcondition checks before returning success. A capability must obey its approved effect boundaries; this in-process host is trusted code.
5. Derive `ExecutionContext` from the authenticated transport and server-controlled Workspace snapshot. Never accept it directly from arbitrary tool arguments. `submit(context, { capability, input, idempotencyKey })` returns the durable Run before asynchronously authorizing/dispatching it.
6. Use `status(owner,id)`, `events(owner,id,afterSequence,limit)`, `wait(owner,id,afterVersion,waitMs)`, and `cancel(owner,id)`. `owner` must also come from trusted authentication. Tool adapters should remove private root paths from responses.
7. `operator.pending(slotId)` and `operator.decide({ approvalId, expectedDecisionVersion, decision, actor })` are separate trusted capabilities. The adapter authenticates the actor; there is no request-level `isAdmin` bypass. A successful approval queues the same Run without caller resubmission.
8. Close with `await kernel.close(drainMs)` before releasing the Slot lock. It owns and closes the store. Concurrent close calls are safe. Shutdown aborts the observation signal with `signal.reason instanceof ExecutionDetached` (`code: CORE_DETACHED`), drains for at most the requested duration, and marks unconfirmed active work UNKNOWN. An independent executor adapter must stop observing and report `UnconfirmedOutcome` on detach, without sending an external cancellation. Only `kernel.cancel` uses the ordinary user cancellation signal. An earlier user cancellation reason is preserved if shutdown follows it. Cancellation does not claim rollback or successful process termination.
9. Drive Core execution readiness from `kernel.health().executionAvailable`, not process liveness. `health()` is a read-only database probe and returns scheduler state, active execution count, a redacted failure code, and storage health. A prior SQLite write/busy failure remains latched even if a later SELECT succeeds; the runtime stops new dispatch until it is reopened after ownership and storage checks. A probe does not guarantee future writes will succeed. Health remains available after shutdown and never expires approvals or changes database rows.

## Policy contract

`authorize(run,input)` returns ALLOW, DENY with a reason, or CONFIRM with a reason and absolute expiry. `revalidate(run,input)` must check current revocations, root authorization, policy hard denials, and bound preconditions. It runs again immediately before dispatch, including for approved Runs; approval is not permission to bypass changed policy. Hooks receive copies of persisted JSON. Immutable context, capability versions, input digest and intent digest are protected from updates by the store schema.

The initial grant is one approval per Run. Session grants, policy rules and OS enforcement are not implemented in this module. Reusing an idempotency key with changed context, capability/binding version or JSON input is an explicit conflict, not a new execution.

Async authorization/revalidation results are discarded if the Run state version changed while awaiting the hook. The latest Run is scheduled again. The hook itself must validate the current external policy revision after its own asynchronous work; a cached boolean computed before a revocation is not sufficient. Expiry is checked again at the durable dispatch point. Version checks do not make arbitrary filesystem or external policy changes transactional with an OS action.

## Persistence and recovery

- WAL, `synchronous=FULL`, foreign keys and short `BEGIN IMMEDIATE` transactions protect state/event/approval/attempt/outbox/receipt consistency.
- Creation, approval state transitions, decisions with resume-outbox, dispatch registration and receipt finalization have atomic database boundaries.
- Outbox dispatch status DISPATCHING deliberately does not prove that an OS action started. A crash in that window produces UNKNOWN. No handler is automatically replayed after the dispatch point.
- Pending approvals survive restart. Approved or previously queued work is revalidated and executed using its pinned binding. Missing bindings wait for registration; conflicting registered versions fail explicitly.
- A matching trusted receipt can resolve UNKNOWN through `store.finish`. This is an internal executor entry point, never an arbitrary client-provided reconciliation override. Duplicate identical receipts are idempotent; changed receipts are rejected.
- SQLite and external actions do not share a transaction. This implementation does not promise external exactly-once execution. A handler can fail after partial effects. No automatic retries or compensating writes are performed.
- Handler exceptions after dispatch produce a FAILED result containing `sideEffectsMayHaveOccurred: true` and `automaticRetryAllowed: false`. FAILED never means that prior writes were rolled back. A successful handler whose receipt cannot be persisted remains unconfirmed; storage failure stops scheduling, and recovery marks that Run UNKNOWN instead of inventing a FAILED receipt.
- Schema creation, indexes/triggers and `user_version` are one transaction. A failed BEGIN is not followed by an invalid rollback; failures during commit/body attempt rollback, retain fault health and fail closed. Failed construction releases its database handle.

## PayloadStore follow-up contract

The current `runs.input`, `runs.result`, and receipt payloads are plaintext JSON. File permissions must cover the database plus WAL/SHM and backups. Hashing input protects identity comparisons, not confidentiality; removing a row would not securely erase old WAL or backup contents. The current runtime therefore accepts only nonsecret payloads in explicitly trusted local use.

A later separate PayloadStore should expose trusted `put(owner, content, policy) -> { ref, digest, size, keyVersion }`, `get(owner, ref, expectedDigest)`, and `release(ref, retentionDecision)` contracts. Run transactions retain immutable references, not secret text. Prepare payload bytes before committing their reference; garbage-collect only unreferenced staged blobs after a grace period. Never delete referenced data for active, approved or uncertain Runs. Bind decryption to authenticated owner/Slot and OS-protected keys, use authenticated encryption, and record SecretRefs instead of long-lived credentials. Unavailable keys or nonpersistable secrets require WAITING_INPUT/explicit recovery rather than automatic replay. Migration must read old plaintext safely, rewrite referenced payloads, verify digest/ownership and account for backups/WAL before claiming confidentiality. None of these encrypted-store guarantees are implemented by this foundation.

## Limits and operations

Inputs and results are bounded to 1 MiB JSON with at most 64 nesting levels. Event pages are at most 500 entries; wait and drain windows at most 30 seconds; approval expiry at most 24 hours. Default concurrency is 4 (maximum 32). Default admission is 10,000 stored Runs (configurable up to 1,000,000); identical-key retries still return the original Run at capacity. Explicit retention/backup maintenance is required; this module never deletes active or uncertain work automatically. SQLite calls are synchronous on the event loop; move storage to a bounded worker before production latency claims.

Inject deterministic time into `new DurableStore(path, { clock })` for approval/event tests. Wait duration uses a monotonic clock so frozen or changed wall time cannot hang a wait. The kernel's expiry sweep runs every second while alive; status, Operator enumeration/decision and startup also enforce expiry. Database failures stop new dispatch, and subsequent public operations fail closed. Error payloads record stable error codes rather than raw handler errors that may expose secrets.

Run `npx tsx src/test/v3-durable.ts` or the compiled equivalent after building. The suite uses real temporary SQLite databases and covers restart recovery, ownership, transactional state transitions, approval CAS, immutable context, idempotency, wait timeout, cancellation, revocation, receipt conflicts, pinned bindings, capacity and bounded concurrent shutdown. Additional fault tests forcibly kill a child process after an external effect, hold a competing SQLite write transaction at admission and receipt finalization, verify atomic schema rollback, expire approved work during asynchronous validation, and change Run versions while a stale validation is suspended.
